# Blackwell Consumer-Class (SM120/SM121) Kernel Constraints

Constraints you will hit writing or porting kernels for NVIDIA GB10 / DGX
Spark (`sm_121a`). Facts about CUTLASS support come from NVIDIA's [Blackwell
functionality documentation](https://docs.nvidia.com/cutlass/latest/media/docs/cpp/blackwell_functionality.html);
per-device limits and compiler target semantics come from the CUDA Programming
Guide's [compute capabilities appendix](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/compute-capabilities.html).

The single most important thing to internalise: **"Blackwell" names two
different machines.** SM100 (datacentre B200-class) and SM120/SM121
(consumer-class, including GB10) share a marketing generation and very little
else at the instruction level. Conflating them causes real bugs, and a
capability check written as "is Blackwell" will select code paths that do not
exist on this target.

## SM120 is not SM100

The two differ in the matrix instruction they issue, which cascades into
everything else:

| | SM100 (datacentre) | SM120/SM121 (consumer) |
| --- | --- | --- |
| Matrix instruction | `tcgen05.mma` family | `mma.sync.aligned` (warp-level) |
| Cluster shape | Multicast, multi-CTA clusters | Fixed `1x1x1`, no multicast |
| Operand layouts | TN, NN, NT, TT | **TN only** |
| CTA group | `cta_group::1` or `::2` | n/a |

SM120's narrow-precision support arrives as extensions to the *warp-level*
`mma` instruction — the same lineage as Ada — rather than the fifth-generation
`tcgen05` tensor-core instructions SM100 uses. NVIDIA characterises the
resulting throughput relative to Ada's FP8 tensor cores (1×-4× depending on
type and accumulator), not relative to SM100.

Consequences:

- **Do not gate on major version alone.** `capability.major == 10` is
  *false* on `sm_121a`. That is correct for anything requiring `tcgen05.mma`,
  and wrong if you meant "Blackwell or newer".
- **A kernel written for SM100 will not simply retarget.** If it relies on
  multi-CTA clusters, multicast, or the `tcgen05` operand model, there is no
  equivalent to relax it into.

### How this shows up in this tree

Three concrete instances, useful as calibration for what "consumer-class
Blackwell" costs in practice:

- **FA4 is gated on major-10, so SM12 uses FA2.** MLA prefill and related
  backends test `device_capability.major == 10`
  (see `vllm/v1/attention/backends/mla/prefill/`), so `sm_121a` takes the FA2
  path. This is a correct gate — FA4 needs SM100 features — but it means
  attention performance on this target is not the FA4 number you may have read
  elsewhere.
- **Attention sinks fall back to generic Triton.** There is no optimized sink
  path for this target, so sink-bearing models serve on the generic kernel.
  Per this fork's requirements, that is a gap to close rather than support.
- **CUTLASS FP8 grouped GEMM needed a newer CUTLASS.** The SM120 pointer-array
  collective used by grouped FP8 MoE only exists in CUTLASS 4.6.1, which is why
  `CUTLASS_REVISION` is pinned there in `CMakeLists.txt`. If you are adding a
  grouped-GEMM path and it compiles but finds no viable collective, check
  whether the collective you need is SM100-only in the pinned version.
- **Compiling is not the same as being worth selecting.** That grouped FP8 MoE
  kernel is correct on both 12.x targets but slower than Triton: measured on
  sm_120 it loses up to 19.7% of output throughput at larger batch sizes, and on
  sm_121a it is at parity apart from a small gain at batch 64. FP8 MoE auto
  selection therefore puts Triton ahead of the vLLM CUTLASS backend for the
  whole 12.x family (`_get_priority_backends` in
  `vllm/model_executor/layers/fused_moe/oracle/fp8.py`). `--moe-backend cutlass`
  still selects it explicitly. When you port an SM100 kernel down to this
  target, benchmark it against the generic path before making it the default —
  "it runs" is not the bar.

## Resource limits

The per-SM budgets differ sharply from SM100, and the shared-memory figure is
the one most often quoted wrongly:

| | SM120/SM121 (12.x) | SM100 (10.x) |
| --- | --- | --- |
| Max shared memory per SM | **100 KB** | 228 KB |
| Max shared memory per thread block | 99 KB | 227 KB |
| Legal shared-memory carve-outs | 0/8/16/32/64/100 KB | 0/8/16/32/64/100/132/164/196/228 KB |
| Unified data cache | 128 KB | 256 KB |
| Max resident warps per SM | 48 | 64 |
| Max resident blocks per SM | 24 | 32 |
| Max resident threads per SM | 1536 | 2048 |
| FP32:FP64 throughput | 64:1 | 2:1 |

Both targets carry 64K 32-bit registers per SM, cap a thread at 255 registers,
and use a warp size of 32.

The 128 KB figure frequently cited as SM12x shared memory is the *unified data
cache* size, not the shared-memory limit — the legal carve-outs stop at 100 KB.
An SM100 kernel tiled against 164-228 KB of shared memory therefore cannot be
allocated on this target at all: that is a launch failure, not a slower path.
Any block wanting more than 48 KB must use dynamic shared memory and opt in
explicitly.

The lower occupancy ceiling matters too. With 48 resident warps against SM100's
64, the same register-hungry kernel loses proportionally more latency hiding
here.

## Compiler targets

The target suffix decides which devices a binary will run on, and the naming is
not self-explanatory:

| Suffix | Meaning | Runs on |
| --- | --- | --- |
| none, e.g. `compute_120` | Baseline features only | 12.0 and later |
| `f`, e.g. `compute_120f` | Family-specific | 12.0 and 12.1 |
| `a`, e.g. `compute_121a` | Architecture-specific | 12.1 only |

Each is a superset of the one above it in features and a subset in portability;
`compute_100f` correspondingly covers 10.0 and 10.3. Architecture-specific
targets appeared with 9.0, family-specific ones with 10.0.

The vLLM wheel, GGUF plugin wheel, runtime stage, and native
`homelab/spark.Dockerfile` set `TORCH_CUDA_ARCH_LIST="12.1a"`. The FlashInfer
cross wheel additionally retains `12.0f` with `12.1a`, because its CUDA 12.9+
runtime resolver requires both AOT module variants.

That matters because an `a` target will not load on a device of any other minor
capability: a `12.1a` binary does not run on SM120 at all, so an RTX 5090 cannot
use it even though both are "SM12x". This is a deployment failure distinct from a
capability gate being wrong in source — the gate can be correct and the kernel
still absent. If you need one artefact to cover both, `12.0f` is the family
target that spans 12.0 and 12.1.

## Tile shapes and schedules

For CUTLASS collective-builder narrow-precision GEMM paths, the valid MMA tile
shapes are a short list,
and the choice interacts with the kernel schedule. Across the block-scaled and
non-block-scaled tables in the CUTLASS reference, the shapes that appear are
`128x128x128`, `256x128x128` and `128x128x256`, **TN only** — with `N` for
every other layout combination.

Two schedules are available, mirroring Hopper's warp-group GEMM:

- **Cooperative** — one group of 8 MMA warps on a single output tile. Selected
  by default when `KernelScheduleAuto` is specified.
- **Pingpong** — two groups of 4 MMA warps on *different* output tiles,
  overlapping mainloop and epilogue.

Not every shape supports both. `256x128x128` is cooperative-only in the tables
where it appears, whereas `128x128x128` and `128x128x256` generally accept
either. Mixed-input `mx_float4_t` kernels additionally require the specialized
`...Mxf8f6f4Sm120` dispatch policies rather than the generic ones. Consult the
tables for your exact type combination rather than assuming — the pattern is
regular but not uniform.

Hand-written SM12x kernels may instead use warp-level `mma.sync` tiles such as
`m16n8k32` (FP8 e4m3) and `m16n8k16` (BF16), constrained by shared-memory
ceiling.

Since the cluster shape is fixed at `1x1x1`, there is no cluster dimension to
tune, and any autotuning space imported from an SM100 configuration that sweeps
cluster shapes has no meaning here.

Be careful not to generalise that into a hardware claim. NVIDIA's
compute-capability feature table lists thread block clusters, distributed shared
memory and TMA as available from 9.0 onward, including 12.x, while CUTLASS fixes
cluster shape at `1x1x1` for these kernels. Whether clusters are usable on this
target outside CUTLASS's GEMM path is not established here — treat `1x1x1` as a
fact about these kernels, not as proof the hardware cannot form clusters.

## Block-scaled and narrow-precision types

Tensor Core input types on 12.x are TF32, BF16, FP16, FP8, FP6, FP4 and INT8.
There is no FP64 tensor-core path and no INT4; SM100 additionally offers FP64.

Blackwell's narrow-precision types are shared between SM100 and SM120 (the data
types and tensor alignment requirements are the same, as is the scale-factor
layout), so this part *does* port. The distinction to keep straight is which
types can serve as scale factors:

| Role | Types |
| --- | --- |
| Operand data | `float_e4m3_t`, `float_e5m2_t` (8-bit); `float_e2m3_t`, `float_e3m2_t` (6-bit); `float_e2m1_t` (4-bit) |
| Scale factor | `float_ue8m0_t`, `float_ue4m3_t` (unsigned, 8-bit) |

Block-scaled types pair an operand type with a scale-factor type and a **scale
factor vector size** — the number of operand elements sharing one scale factor.
This is the layout parameter most likely to be wrong in a port:

| Type | Scale factor | SF vector size (dense) | SF vector size (sparse) | OCP compliant |
| --- | --- | --- | --- | --- |
| `mx_float8_t` | `float_ue8m0_t` | 32 | 64 | Yes |
| `mx_float6_t` | `float_ue8m0_t` | 32 | 64 | Yes |
| `mx_float4_t` | `float_ue8m0_t` | 32 | 64 | Yes |
| `nv_float4_t` | `float_ue4m3_t` | 16 | 32 | No |

Note that `nv_float4_t` is **not** OCP-compliant and uses a different scale
factor type *and* a different vector size (16, not 32) from the `mx_*` family.
Interchanging `nv_float4_t` and `mx_float4_t` therefore mis-groups scale
factors — a failure that produces wrong numbers rather than an error. Sparse
variants double the vector size in every case.

Alignment requirements are reported in *elements*, not bytes. For the legacy
types (`tf32`, `f16`, `bf16`, `i8`, `u8`) alignment matches Hopper and all four
layouts are supported; for narrow precision on SM120, remember the TN-only
restriction above.

## What to check before believing a port works

- Does your capability gate distinguish SM100 from SM120, or does it test
  `major` alone?
- Is your tile shape in the valid table **for your exact type pair**, and does
  your schedule appear against that shape?
- Is your layout TN?
- If block-scaled: does your scale-factor vector size match the type
  (16 for `nv_float4_t`, 32 for `mx_*`, doubled for sparse)?
- Does your shared-memory footprint fit 100 KB per SM and 99 KB per block, and
  have you opted in if it exceeds 48 KB?
- Is the kernel compiled for a target this device will actually load — `12.1a`
  reaches only SM121, `12.0f` reaches 12.0 and 12.1?
- Are you comparing performance against an FA4/SM100 number that this target
  cannot reach, or against what this target currently achieves?

Then apply the [verification bar](verification.md) — a narrow-precision kernel
that is subtly mis-scaled will look plausible without a reference comparison.
